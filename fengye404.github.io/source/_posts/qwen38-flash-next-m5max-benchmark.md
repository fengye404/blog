> 本文由 AI 参与创作。模型部署、测速和数据整理由 Codex 在我的机器上执行，测试时间为 2026 年 10 月 10 日至 11 日。

最近我想在 Mac Studio 上部署 Qwen3.8-Flash-Next，选了两个社区版本来对比：REAP-288 和 mixed-4-8bit。我平时会用到 200K 左右的上下文，所以除了短输入下能跑多快，还想看看输入变长之后，速度和内存占用会怎么变化，MTP 推测解码值不值得开。

这次从 512 token 一直测到接近 256K，分别用了中文、英文和代码，共完成 240 个独立测试项。**在这两套部署方案中，mixed 更适合我这台 128G Mac 的长上下文使用：200K 输入下生成速度约 56 tok/s，开启 MTP 后约 75 tok/s；REAP 占用的内存更少，但长输入下速度下降明显。**

下面先介绍部署配置，再看速度、内存和输出检查，最后整理一下实际使用时怎么选。

## 1. 测试环境和模型版本

这次使用的是满血版 M5 Max Mac Studio：18 核 CPU、40 核 GPU、128 GiB 统一内存，系统为 macOS 27.0。

两个模型都来自 Qwen3.8-Flash-Next，主要区别在于：

- **REAP-288**：对专家做了剪枝，每层从 512 个保留到 288 个，再使用 4-bit 量化，模型文件更小。
- **mixed-4-8bit**：保留 512 个专家，专家权重主要使用 4-bit，Attention 等部分使用 8-bit。下面简称 mixed。

这里的专家可以理解为 MoE 模型里供路由选择的一组子网络。两版处理每个 token 时都激活 10 个专家，所以专家总数减少，并不代表每次计算也按同样比例减少。

| 项目 | REAP | mixed |
| --- | --- | --- |
| 模型仓库 | [sh0wie / REAP-288-MLX-4bit](https://huggingface.co/sh0wie/Qwen3.8-Flash-Next-REAP-288-MLX-4bit) | [ddalcu / MLX-Serve-mixed-4-8bit](https://huggingface.co/ddalcu/Qwen3.8-Flash-Next-MLX-Serve-mixed-4-8bit) |
| 推理引擎 | mlx-vlm 0.7.6 / MLX 0.32.3 | mlx-serve 26.10.1 |
| 全套下载体积 | 73.52 GB，约 68.47 GiB | 107.33 GB，包含约 32 GB 的 ngram 表 |
| MTP 权重 | 另需约 5.24 GB 的 drafter | 模型包内提供 |

为了让结果能对上具体版本，下载时固定了 revision，并对权重做了 SHA-256 校验。完整版本号放在文末的测试配置中。两边使用了不同的权重和引擎，下面的结果反映的是整套部署方案的差异。

**版本更新说明：**整理文章时，[mixed 模型作者已推荐新的 iQ 版本](https://huggingface.co/ddalcu/Qwen3.8-Flash-Next-MLX-Serve-mixed-4-8bit#qwen38-flash-next-for-mlx-serve-4-bit-experts-8-bit-rest)，旧包停止更新。本文仍保留实际测过的 mixed-4-8bit，新版本没有在本机复测。

## 2. 部署时怎么控制内存

Qwen3.8-Flash-Next 还有一张较大的 **ngram embedding 表**，根据相邻 token 的组合查出向量。mixed 模型包中，这张表单独放在 `ngram_table.bin`，约占 32 GB。

这次两套方案都将表留在 SSD 上，通过 **mmap（内存映射）按需读取**：访问到哪部分，就读取对应的文件页，交给系统缓存管理。这样可以减少整表常驻内存的占用。具体设置如下：

| 配置 | REAP | mixed |
| --- | --- | --- |
| ngram 表 | `ple_storage`，SSD mmap | `ngram_table.bin`，SSD mmap |
| 额外设置 | `cache_rows=0` | 关闭 `ple-gpu`，设置 `MLX_SERVE_NGRAM_WARM=0` |
| MLX 缓存上限 | 4 GiB | 8 GiB |
| Prefill 分块大小 | 1,024 | 1,024 |

`MLX_SERVE_NGRAM_WARM=0` 用来关闭整张表的主动后台预热。已经访问过的文件页仍会进入 macOS 缓存，因此 mmap 不等于完全不占内存，也不能把重启模型进程当作清空了 SSD 文件缓存。

测速时，活动监视器里 REAP 的 Python 进程大约占 49 GB，比下载体积小。原因就在于**磁盘文件大小、进程内存、MLX 分配量和系统文件缓存是不同的统计口径**。下面统一列 MLX 在全部速度测试中记录到的最高分配量：

| 方案 | MLX 最高分配量 |
| --- | ---: |
| REAP | 55.46 GB |
| REAP + MTP | 60.68 GB |
| mixed | 80.64 GB |
| mixed + MTP | 84.30 GB |

在本次单模型、单请求测试中，两套方案都能在 128 GiB 内存上跑完；REAP 的余量更大。这里的数值不代表整机总占用，也不能直接与活动监视器的进程内存相加。REAP 按请求记录峰值，mixed 按服务进程记录高水位，并在每个上下文批次重启。

正式请求期间采样到的 Swapouts 增量均为零，也就是没有观察到新增的换出记录。日常还要同时运行哪些应用，仍然需要算进内存预算。

## 3. 从 512 到 256K，速度变化有多大

### 测试方法

输入长度分为八档：512、4,096、16,384、32,768、65,536、131,072、200,000 和 261,632 token。最后一档给 262,144 token 的上下文窗口留出了输出空间，下面简称 **256K 档**。

中文、英文使用固定的 Wikipedia 文本，代码使用 CPython 3.12.0 标准库源码，按长度截取，没有反复复制短文来凑 token。每份输入的前、中、后各插入一个校验码，让模型先提取，再分析内容。

REAP、mixed 分别测试普通模式和 MTP 模式。32K 及以下每项重复三次，64K 及以上重复两次，合计 240 项。其他设置保持一致：

- 每次只加载一个模型，处理一个请求。
- 输出最多 256 token，`temperature=0`，关闭思考。
- 关闭前缀缓存，让每轮重新处理完整输入。
- `prefill chunk=1024`，每批处理 1,024 个输入 token。

读速度表之前，先区分三个指标：

| 指标 | 表示什么 |
| --- | --- |
| Prefill 速度 | 模型每秒处理多少输入 token |
| Decode 速度 | 模型每秒生成多少输出 token |
| 首 token 时间 | 从发送请求到收到第一个输出 token 要等多久，包含分词等开销 |

**长文输入首先要等 Prefill 完成，之后才进入持续生成。**所以生成速度快，并不代表把一份长文发过去就能立刻收到回答。

### 测试结果

![中文、英文和代码在不同输入长度下的 Prefill 与 Decode 速度](/downloads/qwen38-m5max-benchmark/speed-curves.png)

图中实线为普通模式，虚线为 MTP，误差棒表示实际最小值到最大值。完整报告按中文、英文和代码分别统计；下面将同一档三个领域的全部轮次合并，取中位数。

| 输入档位 | 方案 | Prefill（tok/s） | Decode（tok/s） | 首 token 时间（秒） |
| --- | --- | ---: | ---: | ---: |
| 200K | REAP | 1,047.5 | 20.9 | 191.2 |
| 200K | REAP + MTP | 1,044.9 | 19.0 | 191.6 |
| 200K | mixed | 1,855.5 | 56.3 | 108.0 |
| 200K | mixed + MTP | 1,892.6 | 74.8 | 105.9 |
| 256K | REAP | 970.8 | 17.8 | 269.8 |
| 256K | REAP + MTP | 995.1 | 15.1 | 263.2 |
| 256K | mixed | 1,856.5 | 56.0 | 141.1 |
| 256K | mixed + MTP | 1,823.3 | 74.5 | 143.9 |

普通模式下，mixed 在 200K 和 256K 仍能保持约 56 tok/s 的生成速度，REAP 则下降到约 21 和 18 tok/s。处理长输入时，mixed 的 Prefill 也更快，因此对我常用的 200K 上下文来说，mixed 更合适。

不过 mixed 在 256K 档也要等约 141 秒才开始输出。这里关闭了前缀缓存，每次都要重新处理输入；多轮对话复用历史缓存后的等待时间，本轮没有测试。

### MTP 要不要开

MTP（Multi-Token Prediction，多 token 预测）在这里用于推测解码：先由预测模块提出后续 token，再由主模型验证，希望一次验证能接收多个 token，减少逐个生成的开销。预测和验证本身也要计算，实际能否提速，需要测一下。

mixed 在 200K 档从 56.3 提升到 74.8 tok/s，提升约 `(74.8 / 56.3 - 1) × 100% ≈ 33%`；256K 档也有类似收益。但首 token 时间变化不大，MTP 在这里主要加快的是开始输出之后的生成过程。

REAP 在这两个长输入档位都变慢了，还多占约 5 GB 的 MLX 内存。因此，**mixed 可以按需开启 MTP，REAP 用于长上下文时保持普通模式即可。**

另外，对相同输入的首轮完整输出做比较，REAP 两种模式有 24/24 份逐字一致，mixed 只有 3/24 份一致。这个结果只说明当前运行时的输出会变化；如果要复现普通模式的输出，就继续使用普通模式。

## 4. 输出质量检查

速度之外，我们也要看看模型有没有正常回答。这次做了两类简单检查：

| 检查项 | REAP | mixed |
| --- | ---: | ---: |
| 六个简单任务：算术、JSON、排序、逻辑、提取、格式遵循 | 两种模式均通过 5/6 | 两种模式均通过 5/6 |
| 输入前、中、后三个校验码的提取 | 两种模式均命中 177/180 | 两种模式均命中 180/180 |

四种方案都答错了同一个算术样本。REAP 的三次校验码错误来自同一份 4K 英文输入，200K 和 256K 档则全部提取成功。它们说明模型在这些输入下能完成简单任务，复杂长文理解和实际代码修改能力还需要另外测试。本轮没有跑 HumanEval。

还做了一次固定文本预测检查：让模型预测中文、英文和代码里的下一个 token，看看它给正确答案分配了多少概率。用 **NLL（负对数似然）**表示，正确 token 的概率越高，NLL 越低。

受接口最多返回 top-1024 token 概率的限制，96 个采样位置中只有 95 个能同时给两个模型评分：REAP 的平均 NLL 为 2.1034，mixed 为 1.7881。mixed 在这个小样本上更好。由于缺失位置被排除，这个结果会偏向容易预测的 token，不能当作完整语料的困惑度评测。

## 5. 复测时需要注意的地方

这轮测试有两个问题会影响结果核对，单独记录一下。

**第一个是 token 数要以实际引擎为准。**两模型的 tokenizer 文件相同，但原生引擎与 Hugging Face 实现的分词结果存在差异。例如同一份中文长输入，一边统计为 200,020 token，另一边是 200,002。后来通过 `/tokenize` 核对，序列都能还原原文，usage 与原生计数一致，输入加输出预算也没有超出窗口，最终按实际引擎计数计算速度。两套方案收到的是相同文本，token 序列不一定完全相同。

**第二个是加载失败和缓存状态要留下记录。**mixed 在权重预计算阶段出现过六次 GPU 超时，电脑中途也重启过一次，恢复后补跑了缺失批次。264 条原始速度记录里有 24 条重跑，最终每个测试项只采用第一条通过核查的结果，得到 240 项。加载超时的原因尚未确认。

macOS 文件缓存没有强制清空，首轮编译和读页的耗时保留在结果里；测试也跨过重启，两个请求期间执行过短暂的 CPU 分词核查。完整报告保留了波动范围，复测时可以一起对照。

## 6. 实际使用时怎么选

如果同样使用 128G M5 Max，可以先按自己的需求选：

| 使用需求 | 本轮测试后的选择 |
| --- | --- |
| 常用 200K 左右的长上下文 | 这两套方案中优先 mixed，普通模式约 56 tok/s |
| 希望长输入后生成得更快 | mixed 开启 MTP，约 75 tok/s，同时检查自己的任务输出 |
| 希望给其他应用多留内存 | REAP 普通模式，MLX 峰值约 55 GB |
| 需要复现普通模式的回答 | 保持普通模式，不切换 MTP |

配置上，**先沿用 SSD mmap 加载 ngram 表、关闭整表主动预热、Prefill 分块设为 1,024 这组已经测过的设置**，再根据自己的任务调整。测试中关闭前缀缓存，是为了比较完整输入的处理成本；日常多轮对话是否启用、启用后能省多少时间，需要单独验证。

这次主要测清楚了长输入下的速度和内存占用，输出预算只有 256 token，还没有覆盖长回答、并发请求和复杂问答。后续继续测这些场景，再更新实际使用的配置。

> 本文由 AI 参与创作。模型部署、测速和数据整理由 Codex 在我的机器上执行，结论来自本机实测。测试时间为 2026 年 10 月 10 日至 11 日。

最近我想在 Mac 上部署一个 Qwen 系列模型，挑中了两个 Qwen3.8 Flash Next 的社区版本：一个做了专家剪枝，另一个保留更多专家、使用混合量化。我平时会开到 200K 上下文，所以只看几百 token 的速度没什么用。于是把测试上限直接拉到 256K，中文、英文和代码都跑了一遍。

这一轮最后留下了 240 个独立测试项。两个模型都把 ngram 表放在 SSD 上，通过 mmap 按需读取，也分别测试了普通生成和 MTP 推测解码。

先看结果。

**对我这台 M5 Max / 128 GiB，mixed 更适合长上下文；REAP 的优势是内存余量。mixed 开 MTP 能继续提速，REAP 开 MTP 在长上下文下反而变慢。**

## 两个模型，测的是整套部署方案

| 项目 | REAP | mixed |
| --- | --- | --- |
| Hugging Face 仓库 | [sh0wie / REAP-288-MLX-4bit](https://huggingface.co/sh0wie/Qwen3.8-Flash-Next-REAP-288-MLX-4bit) | [ddalcu / MLX-Serve-mixed-4-8bit](https://huggingface.co/ddalcu/Qwen3.8-Flash-Next-MLX-Serve-mixed-4-8bit) |
| 专家数 | 288 | 512 |
| 每 token 激活专家 | 10 | 10 |
| 推理引擎 | mlx-vlm 0.7.6 / MLX 0.32.3 | mlx-serve 26.10.1 |
| 全套下载体积 | 73.52 GB，约 68.47 GiB | 107.33 GB，含约 32 GB ngram 表 |
| ngram 加载 | SSD mmap，cache_rows=0 | SSD mmap，关闭整表后台预热 |

机器是 Mac Studio，Apple M5 Max，18 核 CPU、40 核 GPU、128 GiB 统一内存，系统为 macOS 27.0。

我固定了模型 revision，下载后对权重做 SHA-256 校验。REAP 使用 `668f31bcc56bf9400e64c9463445eee47597c2d9`，mixed 使用 `31919167b2e4549167cd4729b782f3155e75b686`。REAP 的 MTP drafter 另占约 5.24 GB。

这里比较的是两套实际可用的部署：权重不同，引擎也不同。速度差异不能全部算在剪枝或量化头上。专家从 512 剪到 288，也不代表计算量按比例下降，因为两者每个 token 都激活 10 个专家。

## 怎么测

输入长度用了 512、4,096、16,384、32,768、65,536、131,072、200,000 和 261,632 八档。最后一档对应 262,144 token 的原生上下文窗口，给输出留空间，文中简称 256K 档。

中文和英文取固定 Wikipedia 文本，代码取 CPython 3.12.0 标准库源码，截取真实语料前缀，没有循环拼接一段短文凑长度。每份输入在前、中、后插入三个校验码，要求模型先提取，再分析文本或代码。

短至 32K 的输入重复三次，64K 及以上重复两次。四种方案乘三类输入，合计 240 项。输出预算统一为 256 token，temperature=0，关闭思考和前缀缓存，prefill chunk=1024，始终只加载一个大模型。

Prefill 是处理输入的速度，decode 是生成输出的速度，首 token 时间包含请求和分词等开销。完整报告按领域分别列中位数和最小—最大值。下文总表把同一档三个领域的全部轮次合并取中位数。

缓存得说清。

mixed 设置了 `MLX_SERVE_NGRAM_WARM=0`，不主动把整张 ngram 表预热进文件缓存；macOS 自己的页缓存仍然存在，也没有强制清空。进程刚启动，并不等于 SSD 缓存是冷的。首轮的新形状编译、按需读页会拉低速度，这些轮次都保留了。

## 从 512 到 256K，速度怎么变

![中文、英文和代码在不同输入长度下的 prefill 与 decode 速度](/downloads/qwen38-m5max-benchmark/speed-curves.png)

图中实线为普通模式，虚线为 MTP；误差棒是实际最小到最大值。连线仅连接测量点。

先看我最关心的两个长输入档位：

| 输入档位 | 方案 | Prefill tok/s | Decode tok/s | 首 token 秒 |
| --- | --- | ---: | ---: | ---: |
| 200K | REAP | 1,047.5 | 20.9 | 191.2 |
| 200K | REAP + MTP | 1,044.9 | 19.0 | 191.7 |
| 200K | mixed | 1,855.6 | 56.3 | 108.0 |
| 200K | mixed + MTP | 1,892.6 | 74.8 | 105.9 |
| 256K | REAP | 970.8 | 17.8 | 269.8 |
| 256K | REAP + MTP | 995.1 | 15.1 | 263.2 |
| 256K | mixed | 1,856.5 | 56.1 | 141.1 |
| 256K | mixed + MTP | 1,823.3 | 74.5 | 143.9 |

mixed 跑起来挺快的。普通模式下，输入从 512 增长到 256K，decode 从约 66.8 tok/s 降到 56.1；REAP 则从约 43.5 降到 17.8。到长上下文时，两套方案的差距比短输入时更大。

但 256K 首次输入依然要等：mixed 普通模式的首 token 中位数约 141 秒。这个测试关闭了前缀缓存，不能拿来预测日常多轮对话复用历史缓存后的等待时间。

### MTP 的收益要单独看

mixed 在 200K/256K 开启 MTP 后，decode 约提高 33%。代码场景的收益更大，完整图里能看到领域差异。

REAP 就有点坑。它的 MTP 在这两档分别降到约 19 和 15 tok/s，还额外占用内存。对我的长上下文用途，没有开它的理由。

我还比较了相同输入下的首轮完整输出。REAP 普通模式与 MTP 有 24/24 份逐字一致；mixed 只有 3/24 份一致。mixed 的校验码命中没有下降，但这份小测试不足以证明其他任务质量不变。需要复现普通模式输出时，我会保留普通模式。

## 内存为什么比模型文件小

测速中我看了一眼活动监视器，REAP 的 Python 进程大约 49 GB，跟下载时看到的体积差不少。其实模型文件、MLX 分配量、进程内存和系统文件缓存是不同口径。

ngram 放在 SSD 上，访问过的文件页仍会进入 RAM 缓存，内存紧张时再回收。它没有消失，也不需要整张表始终作为 GPU 活跃分配驻留。

| 方案 | 全部速度测试的 MLX 最高分配量 |
| --- | ---: |
| REAP | 55.46 GB |
| REAP + MTP | 60.68 GB |
| mixed | 80.64 GB |
| mixed + MTP | 84.30 GB |

这些数值不能和活动监视器中的 RSS 直接相加。REAP 每次请求重置 MLX 峰值，mixed 取当前服务进程的高水位；后者每个上下文批次重启。两边的 MLX 缓存上限也不同，分别为 4 GiB 和 8 GiB。

128 GiB 跑两者都够用。REAP 留给其他应用的空间更多。正式请求采样到的系统 Swapouts 增量均为零，但系统原有 swap 和文件缓存仍会影响运行环境，不能把这个结果扩展成所有并发负载下都不会换页。

## 输出质量和“困惑度”测到了什么

四种方案的六个简单任务都通过了五个，同一个算术样本答错。这个规模只能当冒烟测试，本次也没有在本地跑 HumanEval。

检索校验码方面，REAP 两种模式各为 177/180，mixed 两种模式各为 180/180。REAP 的三次错误来自同一份 4K 英文输入的同一个码。200K 和 256K 的校验码全部通过，但三个短码提取通过，远远不能代替复杂长文理解测试。

我原本还想直接对比困惑度，接口在这里卡住了：原生引擎最多返回 top-1024 logprobs，拿不到任意目标 token 的完整概率。于是采用固定中英代码文本上的 96 个采样位置，比较两边共同可评分的 95 个位置。

| 方案 | 共同位置平均 NLL | exp(平均 NLL) |
| --- | ---: | ---: |
| REAP | 2.1034 | 8.1937 |
| mixed | 1.7881 | 5.9780 |

分数上 mixed 更好。这里的 exp(NLL) **不能当作完整语料 PPL**：样本很少，而且只取共同可评分的位置，会偏向容易预测的 token。缺失概率没有用伪数值补齐，REAP 的 logits 归一化也改成了 FP32，避免低精度舍入。

## 这轮测试踩的坑

最开始报告只列已完成的结果，我又优先跑了 200K/256K，页面上就出现了从 512 直接跳到 200K 的情况。看起来像漏测了。后来补上完整覆盖表，才把待测、正在测和校验异常分开。

另一个坑是分词。两模型的 tokenizer 文件相同，但原生引擎和 Hugging Face 的实现给出了不同序列。例如同一份中文长输入，前者返回 200,020 token，后者是 200,002。早期校验把这些记录排除了。

后来通过 `/tokenize` 单独核对，所有异常输入的两套序列都能完整还原原文，usage 与原生分词计数一致，实际输入加输出预算也没有超出窗口。最终按实际引擎 token 数计速，保留分词差异说明。两边收到的是相同文本，这仍然不能解释为完全相同 token 序列下的对照实验。

加载也翻车了。mixed 在权重预计算阶段记录了六次 GPU 超时；电脑中途还重启过一次。最后把缺失批次单独补跑成功，才凑齐 240 项。原始文件共 264 条速度记录，多出的 24 条重跑没有重复加权，统计采用每个测试项第一条通过核查的结果。

补测成功。

但加载超时的根因还没确认，不能写成稳定性问题已经修好了。测试跨重启和恢复过程，系统缓存状态也不完全一致；两个请求期间还执行过短暂的 CPU 分词核查。这是一台日常使用的电脑上的部署评测。

跑这种长任务，又回到了我写 TermPilot 时那个念头：人不能一直钉在显示器前。至少这次检查点和原始记录留住了，重启后不用整晚重来。

## 我会怎么选

日常 200K/256K，我会先用 mixed 普通模式。需要更快生成时再开 MTP，并接受它在这套运行时上输出会变化这个事实。REAP 留给更重视内存余量的场景，长上下文保持普通模式。

这轮每次只生成最多 256 token，没有覆盖长输出、并发、多轮缓存命中和复杂问答。完整的八档速度、中文英文代码分组、首轮波动和内存峰值都放在下面，查自己的使用场景比只看一张总榜更有用。
